# Dayflow Sync — настройка клиент-серверного взаимодействия

Как связать приложения Dayflow (Windows и macOS) с сервером синхронизации: что настроить на сервере, что в клиенте, какие нужны сетевые доступы и как проверить, что всё работает.

Что умеет система: `docs/dayflow-sync-overview.md`. Контракт API: `docs/sync-server-design.md`. Справочник по серверу (все переменные, эндпоинты, безопасность): `server/README.md`.

---

## 1. Схема

```
 Dayflow (Windows / macOS)                      Dayflow Sync Server (megaserv)
 ┌───────────────────────┐   HTTP, :8790        ┌──────────────────────────────┐
 │ push / pull / stream  │ ───────────────────► │ Fastify (Node 24)            │
 │ токен устройства dfd_ │   Bearer <токен>     │   └─ PostgreSQL 17 (внутри   │
 └──────────┬────────────┘                      │      compose-сети)           │
            │ вход                              └──────────────┬───────────────┘
            ▼                                                  │ обмен code → токены,
 системный браузер ──► accounts.google.com                     │ проверка ID-токена
            │                                                  ▼
            └─► http://127.0.0.1:<порт>/callback      oauth2.googleapis.com, www.googleapis.com
                (локальный приёмник в приложении)

 Браузер (дашборд) ── cookie df_session ──► тот же адрес сервера, путь /
```

- Клиент знает только **адрес сервера**. Всё остальное (Google client ID, проекты, пространства) он получает от сервера.
- Client secret Google хранится только на сервере. Клиент отдаёт серверу одноразовый code и PKCE-verifier, сервер сам меняет их на токены.
- После входа у каждого компьютера свой **токен устройства**. Им подписаны все запросы синхронизации. Токен можно отозвать.

## 2. Сетевые требования

| Откуда | Куда | Зачем |
|---|---|---|
| Компьютер с Dayflow | `http://192.168.0.90:8790` (TCP 8790) | синхронизация, SSE-поток, дашборд |
| Компьютер с Dayflow | `https://accounts.google.com` | окно входа в браузере |
| Браузер на том же компьютере | `http://127.0.0.1:<случайный порт>` | возврат из Google в приложение; внешних портов не открывает |
| Сервер | `https://oauth2.googleapis.com`, `https://www.googleapis.com` | обмен code на токены и ключи для проверки ID-токена |
| Сервер | адрес Odoo | только для таймшитов, если подключён Odoo |

- Сейчас сервер доступен **только из сети компании** (LSZ и площадки через WireGuard). Из дома нужен VPN.
- Postgres наружу не публикуется.
- SSE-соединение `/api/sync/stream` держится постоянно. Сервер шлёт `ping` каждые 25 секунд. Прокси и файрволы между клиентом и сервером не должны рвать соединения, молчащие меньше минуты.

## 3. Сервер

Делается один раз администратором. Подробности: `server/README.md`.

1. **Развернуть.** С рабочей машины с SSH-доступом к megaserv:
   ```bash
   server/deploy.sh
   ```
   Скрипт загружает исходники в `/srv/dayflow/src`, при первом запуске создаёт `/srv/dayflow/.env` (права 600), собирает образ на хосте, поднимает compose-проект `dayflow` и проверяет `/api/health`.
   Параметры подключения переопределяются переменными окружения: `DEPLOY_HOST` (по умолчанию `192.168.0.90`), `DEPLOY_SSH_PORT` (`60022`), `DEPLOY_USER`, `DAYFLOW_PORT` (`8790`), `DAYFLOW_PUBLIC_URL`, `DAYFLOW_BOOTSTRAP_ADMIN_EMAILS`.

2. **Создать OAuth-клиент Google** типа **Desktop app** и записать его в `.env`:
   ```
   GOOGLE_CLIENT_ID=…apps.googleusercontent.com
   GOOGLE_CLIENT_SECRET=…
   ```
   Пошагово: раздел «Google sign-in» в `server/README.md`. Redirect URI регистрировать не нужно: клиент типа Desktop app принимает любой порт на `127.0.0.1`.

3. **Проверить переменные, которые влияют на клиентов:**

   | Переменная | Что задаёт |
   |---|---|
   | `PUBLIC_URL` | адрес, под которым сервер видят клиенты. Из него строятся ссылки на дашборд и приглашения. Должен совпадать с тем, что вписано в клиенте |
   | `ALLOWED_EMAIL_DOMAINS` | кто может войти: домены и/или точные адреса через запятую, например `velesagro.pl,someone@gmail.com`. Пусто — любой подтверждённый Google-аккаунт (до приглашения он ничего не видит) |
   | `BOOTSTRAP_ADMIN_EMAILS` | эти адреса при первом входе становятся owner пространства по умолчанию. Входить им можно всегда |
   | `DEV_AUTH` | `1` включает вход по e-mail без Google. Только для тестовых стендов: `deploy.sh` с ним не деплоит |
   | `AUTH_RATE_LIMIT` | лимит запросов входа в минуту с одного IP (20) |

4. **Перезапустить** после правки `.env`: `server/deploy.sh` (или `$DC restart dayflow-server` на хосте).

5. **Проверить** с любого компьютера в сети:
   ```bash
   curl http://192.168.0.90:8790/api/health
   # {"ok":true,"version":"…","time":…,"devAuth":false,"googleConfigured":true}
   ```
   `googleConfigured: false` — клиенты не смогут войти, проверьте `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`.

## 4. Клиент

Одинаково на Windows и macOS: **Настройки → «Sync & team»**.

### Подключение

1. **Server.** По умолчанию уже стоит `http://192.168.0.90:8790`. Для другого сервера вписать его адрес и нажать **Save**.
   - Адрес должен начинаться с `http://` или `https://`. Хвостовой `/` убирается.
   - Поменять адрес можно только **до входа**. Если вход уже выполнен, сначала **Sign out**.
2. Приложение само проверяет сервер (`GET /api/auth/google/config`):
   - «Server ready» / кнопка входа активна — можно входить;
   - «Can't reach the server…» — нет связи (см. раздел 7), кнопка **Retry**;
   - «Google sign-in isn't set up on this server yet» — на сервере не задан OAuth-клиент (раздел 3, шаг 2).
3. **Sign in with Google.** Открывается системный браузер, выбирается аккаунт. После этого вкладка показывает «Signed in to Dayflow», её можно закрыть. На вход отводится 5 минут, кнопка **Cancel** прерывает ожидание.
4. После входа:
   - компьютер появляется в списке **Devices** под своим именем (имя хоста);
   - на сервер уходят карточки за последние **30 дней**, затем общие настройки (категории, стендапы, цели дня);
   - с сервера приходят записи с других компьютеров, проекты и пространства.

### Что уходит с компьютера

Блок «What leaves this PC» (на Mac «What leaves this Mac») в том же разделе. Фильтр работает на компьютере, до отправки.

| Настройка | По умолчанию | Действие |
|---|---|---|
| Never upload cards in these categories | `Personal` | карточки этих категорий не покидают компьютер; копии, уже лежащие на сервере, стираются |
| Upload work without a confirmed project as "Out of scope" | вкл. | работа без подтверждённого проекта уходит только как время, без описания. Если выключить, она уходит полностью |
| Upload observations | выкл. | сырые описания экрана от ИИ. Выключение удаляет уже загруженные |

Карточки с пометкой «приватно» не уходят никогда. Скриншоты, таймлапсы, accessibility-лог и чат не синхронизируются вообще.

### Строка статуса

`Last sync 2 min ago · 0 pending changes · live` и кнопка **Sync now**.

- **pending** — изменения, которые ещё не дошли до сервера (например, без сети).
- **live** — открыт SSE-поток, изменения с других машин приходят за секунды. **polling** — потока нет, клиент забирает данные раз в минуту.
- Красная точка и текст — последняя ошибка (раздел 7).

### Где клиент хранит настройки

| | Адрес сервера, курсор, очередь | Токен устройства |
|---|---|---|
| Windows | `%APPDATA%\Dayflow\chunks.sqlite` | `%APPDATA%\Dayflow\secrets.bin` (DPAPI), в интерфейс не передаётся |
| macOS | база Dayflow (StorageManager) | связка ключей (login Keychain) |

## 5. Как идёт обмен

| Что | Когда |
|---|---|
| Push (`POST /api/sync/push`) | через 3 с после локального изменения (изменения собираются в пачку), до 1000 изменений за запрос |
| Pull (`GET /api/sync/pull?cursor=`) | по сигналу `changed` из SSE (через 0,3 с), перед каждым push и раз в минуту |
| Поток (`GET /api/sync/stream`) | открыт всё время, пока выполнен вход. Если 70 с не пришло ни байта, клиент переподключается |
| Повтор после ошибки | 5 с, 10 с, 20 с … до 5 минут. Переподключение потока: 2 с … до 60 с |
| Таймауты запросов | 30 с обычные, 60 с push/pull, 120 с отправка таймшитов в Odoo |

Порядок цикла: сначала pull (чтобы учесть правки с других машин), потом push. Без сети приложение работает как обычно, очередь отправляется, когда связь вернётся.

Сервер отклоняет изменение, если часы компьютера ушли вперёд больше чем на 5 минут (`hlc_in_future`). На всех компьютерах должно быть включено автоматическое время.

**Веб-дашборд.** Кнопка «Open web dashboard» запрашивает у сервера одноразовую ссылку на 60 секунд и открывает её в браузере. Сервер ставит cookie сессии на 12 часов. Дашборд открывается по тому же адресу, что указан в `PUBLIC_URL`.

## 6. Смена адреса сервера, домен и HTTPS

Для доступа извне сети или по имени вместо IP:

1. Поставить перед сервером обратный прокси с TLS (nginx, Caddy и т. п.), проксировать на `http://192.168.0.90:8790`.
   - Для SSE буферизацию отключать не нужно: сервер сам шлёт `X-Accel-Buffering: no` и `Cache-Control: no-cache, no-transform`. Таймаут чтения у прокси должен быть больше 25 секунд (у nginx по умолчанию 60).
2. В `/srv/dayflow/.env`:
   ```
   PUBLIC_URL=https://dayflow.example.com
   TRUST_PROXY=1
   ```
   С `https` cookie дашборда получает флаг `Secure`. `TRUST_PROXY=1` нужен, чтобы лимиты входа считались по реальному IP клиента, а не прокси.
3. Перезапустить сервер.
4. На каждом компьютере: **Sign out → Server → новый адрес → Save → Sign in with Google**. Собственные записи компьютера при выходе остаются и снова уйдут на сервер после входа.

Если адрес меняется, а база та же, пользователи и пространства сохраняются. Если сервер новый (пустая база), он заново наберёт данные с компьютеров, но только за последние 30 дней.

## 7. Диагностика

| Симптом в клиенте | Причина | Что делать |
|---|---|---|
| `Could not reach the sync server (…)` | нет маршрута до сервера, VPN выключен, сервер лежит, неверный адрес | `curl <адрес>/api/health` с этого компьютера; на сервере `server/deploy.sh status` и `logs` |
| `Google sign-in isn't set up on this server yet` | на сервере пустые `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | раздел 3, шаг 2 |
| В браузере «Sign-in failed» / `Sign-in timed out` | вход отменён, истекли 5 минут, ответ пришёл из старой вкладки входа | повторить вход |
| `403 Forbidden: domain_not_allowed` при входе | адрес не входит в `ALLOWED_EMAIL_DOMAINS` | добавить домен или адрес в `.env` и перезапустить сервер |
| `403 Forbidden: account_mismatch` при входе | этот e-mail уже привязан к другому Google-аккаунту | войти тем Google-аккаунтом, которым входили раньше |
| `The server rejected this device (signed out or revoked)` | устройство отозвали в списке Devices или с другого компьютера | **Sign in with Google** заново. Локальные данные сохранены |
| `N changes were rejected by the server: hlc_in_future` | часы компьютера спешат больше чем на 5 минут | включить синхронизацию времени, затем **Sync now** |
| `… rejected …: forbidden` / `forbidden_project` | изменение проекта без роли admin, или привязка к проекту чужого пространства | проверить роль в дашборде (Members) |
| Статус всё время `polling` | прокси или файрвол рвёт долгие соединения | данные всё равно приходят раз в минуту; для live проверить таймауты прокси (раздел 6) |
| `Sign out before changing the server.` | попытка сменить адрес при выполненном входе | сначала **Sign out** |
| Нет проектов после вступления в пространство | приглашение не принято или принято под другим e-mail | войти под тем e-mail, на который выслано приглашение, открыть ссылку, затем **Sync now** |

Полезные проверки на сервере:

```bash
server/deploy.sh status     # контейнеры и /api/health
server/deploy.sh logs       # последние 200 строк лога (тела запросов и токены не пишутся)
```

## 8. Тестовый стенд

Для проверки клиента без Google:

```bash
server/deploy.sh e2e        # временный стенд с DEV_AUTH=1 на 127.0.0.1:18790 у megaserv, после прогона удаляется
```

На стенде с `DEV_AUTH=1` в клиенте под кнопкой Google появляется поле **Dev sign-in**: вход по e-mail без проверки. На рабочем сервере этот режим выключен, и `deploy.sh` откажется деплоить с `DEV_AUTH=1`.
